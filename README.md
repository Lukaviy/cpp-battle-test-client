# Мысли

Здесь реализация в духе Entity Component только без System.
Тут я не стеснялся вайбкодить.

Идея примерно похожая на ту что сделана в master ветке.
Eсть Entity - класс контейнер. Есть компоненты, тоже классы объединяющие данные и поведение.

Взаимодействие осуществляется через события, которые эмитятся на Entity и обрабатываются всеми компонентами, которые реализуют нужный интерфейс. 

Событие представляет собой класс с виртуальными методами.

Например:
```cpp
    // Notified at the start of the owner's own turn. Used by ticking effects (poison).
    struct ITurnTick
    {
        virtual ~ITurnTick() = default;

        virtual void onTurnTick(World& world, Entity& self) = 0;
    };
```

Для того чтобы компонента обрабатывала это событие нужно унаследоваться от `Component<ITurnTick>` и реализовать метод `onTurnTick`.

```cpp
class PoisonEffect : public core::Component<core::ITurnTick, core::IDamageObserver>
{
public:
    void onTurnTick(core::World& world, core::Entity& self) override
    {
        // Implementation
    }

    void onDamageReceived(const core::Damage& damage) override
    {
        // Implementation
    }
};
```
Подписываться можно сразу на несколько событий.

чтобы вызвать событие, нужно вызвать `emit` на Entity, указав указатель на метод интерфейса:
```cpp
target.emit<&IDamageModifier::modifyIncoming>(damage);   // broadcast (только void)
target.emit<&IDamageObserver::onDamageReceived>(damage);
bool used = self.callAny<&ITurnAction::tryExecute>(world, self); // первый, кто вернул true
auto x = self.callFirst<&IHealth::current>();                    // первый реализатор
```

Вызвать можно как у всех кто реализует интерфейс, так и какого нибудь одного.

Получать компоненты из Entity можно не только по типу компоненты но и по интерфейсу которые она реализует. 
Это позволяет легко менять реализацию механики (например, заменить `HealthComponent` на `InvulnerableHealth`) без правок в коде, который запрашивает здоровье.
```cpp
auto health = entity.get<IHealth>();
```
Также можно менять поведение при атаке или движении.

Компонента поведения берет интерфейс `IMove` и вызывает у него `move()`.
Та уже может делать то что ей нужно в зависимости от реализации.

Таким образом получается своего рода Dependency Injection.
Где компоненте не нужно знать кто именно реализует интерфейс, а просто запрашивать его и вызывать методы.
Можно будет изменить поведение передвижения просто заменив реализацию с одной на другую.

В идеале в компоненте еще нужно указать список интерфейсов которые ей необходимы для работы, чтобы ассертить если их нет при добавлении объекта.

В целом на этом основные идеи описаны, внизу сгенеренное описание от ИИ.

# Архитектура решения

## Цели
- Юниты собираются из независимых блоков поведения, а не описываются монолитным классом.
- Добавление нового юнита (Маг, Башня, Ворон) и новой механики (эффекты, модификаторы, типы движения) выполняется без правок ядра.
- Несколько разработчиков могут параллельно расширять систему, не пересекаясь в одних и тех же файлах.
- Поведение наблюдаемо и детерминировано: пошаговая симуляция, явный RNG-сервис, агрегация урона за ход.

## Ключевые понятия

### Entity = мешок компонентов
`Entity` — это `EntityId` плюс упорядоченный список компонентов. Сам `Entity` ничего не знает ни о здоровье, ни об атаке, ни о движении. Всё — в компонентах.

### Component = данные + интерфейсы (CRTP)
Компонент наследуется от `Component<I1, I2, ...>` и тем самым:
1. подключает `BaseComponent` (виртуальный деструктор, владелец, флаг `_alive`),
2. реализует перечисленные интерфейсы,
3. экспортирует `using ImplementedInterfaces = InterfaceList<I1, I2, ...>;` — это единственный источник правды о том, какие интерфейсы реализует компонент. `Entity` использует список при `add<C>()` для построения индексов.

```cpp
class HealthComponent : public Component<IHealth> { ... };
class PoisonEffect : public Component<ITurnTick, IDamageObserver> { ... };
```

`InterfaceList` намеренно сделан простым `template<class...>` — он компилируется быстрее, чем `std::tuple`, и не несёт лишней value-семантики.

### Получение компонентов: по конкретному типу и по интерфейсу
```cpp
entity.get<HealthComponent>();   // конкретный тип
entity.get<IHealth>();           // первый компонент, реализующий интерфейс
entity.forEach<ITurnAction>(fn); // все компоненты с этим интерфейсом
```
Индекс по интерфейсам строится при `add<C>()` через `ImplementedInterfaces`. В горячем пути нет ни `dynamic_cast`, ни RTTI.

### Идентификация типов
`ComponentTypeIdRegistry::getId<T>()` возвращает компактный `uint32_t` (через шаблон `TypeRegistry<TypedId>`). Это позволяет хранить индексы как `std::vector<...>`, индексируя по числу, а не по `std::type_index`.

### Диспетчеризация событий через указатели на методы
```cpp
target.emit<&IDamageModifier::modifyIncoming>(damage);   // broadcast (только void)
target.emit<&IDamageObserver::onDamageReceived>(damage);
bool used = self.callAny<&ITurnAction::tryExecute>(world, self); // первый, кто вернул true
auto x = self.callFirst<&IHealth::current>();                    // первый реализатор
```
- Имя интерфейса извлекается из указателя на метод (`MethodTraits`), пользователю его повторять не нужно.
- `emit` запрещает не-`void` методы статической проверкой — иначе непонятно, чьё значение возвращать.
- Порядок обработчиков детерминирован — порядок добавления компонентов.

### Снапшот-итерация и реентерабельность
Любой `emit/callFirst/callAny/forEach` копирует список целевых компонентов на стек и итерируется по копии. Поэтому обработчик безопасно может:
- удалять свой или чужой компонент (`entity.remove<C>()` помечает как `_alive=false`),
- добавлять новый компонент (он будет виден на следующих вызовах, не в текущем),
- эмитить вложенные события.

`Entity::compact()` физически удаляет помеченные компоненты на границе шага. Похожая стратегия для entity на уровне `World`: `destroyEntity()` ставит флаг `_pendingDestroy`, итерация идёт по индексу, физическое удаление — в конце `step()`. Межссылки между компонентами хранятся как `EntityId`, не как сырые указатели.

### Поворот хода: `ITurnAction` + приоритеты
`World::step()` для каждой живой entity:
1. рассылает `ITurnTick::onTurnTick` (тикают эффекты вроде яда),
2. собирает все `ITurnAction` компоненты, сортирует по `priority()`,
3. вызывает `tryExecute` по порядку до первого `true` — этот action «съедает» ход.

Порядок поведения юнита кодируется не порядком добавления компонентов, а явным `priority`, что устойчиво к рефакторингу фабрик. Фактическая раскладка приоритетов задаётся в фабрике юнита (`Swordsman.hpp`, `Hunter.hpp`).

### Урон как пайплайн
`core::applyDamage(world, target, damage)` — единственный способ нанести урон:
1. `IDamageModifier::modifyIncoming` — броня, иммунитеты, удвоения.
2. `IHealth::applyDamage` — изменение HP.
3. `IDamageObserver::onDamageReceived` — наблюдатели (логи, on-hit-триггеры, флаги для будущих модификаторов — например, отметка «в этот ход был получен Rending» для PoisonEffect).
4. `DamageAccumulator::add` — копит суммарный урон по паре `(attacker, target)`.
5. На лимите `_alive == false` — событие `UNIT_DIED` и `World::destroyEntity`.

`DamageAccumulator::flush()` вызывается между фазами шага и отдаёт **одно** событие `UNIT_ATTACKED` с суммарным уроном — это требование формата ТЗ выполняется автоматически даже для тика яда + Rending в один ход.

### Атрибуция яда
`PoisonEffect` хранит `EntityId source` и эмитит `applyDamage(...)` от имени охотника, наложившего эффект. Если охотник умер — id остаётся валидным «логически» (источник засчитывается).

### RNG как сервис
`IRandom` инжектится в `World` через конструктор. По умолчанию — `DefaultRandom(mt19937)`. Тесты могут подсунуть детерминированный мок без правок логики. Метод `roll(chance, scale)` инкапсулирует «вероятность `chance/1000`» в одной точке.

### Spatial-запросы в `World`
- `queryAdjacent(selfId, from, out)` — соседи (Chebyshev = 1).
- `queryRing(selfId, from, minR, maxR, out)` — кольцо для дальних атак.
- `Map::tryStepToward(from, target, out)` — шаг к цели по правилам 8-связности.

Это убирает копипасту циклов по сетке из всех action-компонентов.

## Расширение: как добавить нового юнита

На примере планируемых юнитов:

- **Маг.** Берёт `RangedAttackAction(spirit, 2, range)` из общего набора, добавляет свою `FirewallAbility` (отдельный action или эффект-сущность типа «огненная стена»). Никаких правок ядра.
- **Башня.** Не добавляет `MoveToTargetAction` и `MoveTargetComponent`. Реализует `IHealth` через `InvulnerableHealth` (игнорирует урон). Добавляет `OccupiesAreaComponent{2,2}`, который при размещении регистрирует на карте 4 клетки. Только новые компоненты.
- **Ворон.** Своя реализация `ISpatial` с `blocksTile() == false`, своя реализация `IMovement` со скоростью 2, опциональный `IDamageModifier`, режущий входящий ranged-урон по особым правилам. Опять же — без правок существующих юнитов.

Один юнит = одна папка во `Features/<Unit>/`. 20 разработчиков почти не пересекаются.

## Преимущества
- **Композиция вместо наследования.** Поведение собирается из готовых блоков; «летает», «неуязвим», «занимает 2×2» — это компоненты, а не модификаторы базового класса.
- **Полиморфизм через интерфейсы, выбор через `get<I>()`.** Подмена реализации (`HealthComponent` → `InvulnerableHealth`) не требует правок в call-sites.
- **Единый источник правды о реализуемых интерфейсах** — `ImplementedInterfaces`. Дублирование исключено.
- **Безопасная реентерабельность** за счёт snapshot-итерации и tombstone-удаления; обработчики не могут разрушить мир под собой.
- **Детерминированный порядок** обработчиков и приоритетов.
- **Низкие накладные расходы.** Нет RTTI в hot path: id типов компактные, индексы — `std::vector`, диспетчеризация — прямой вызов через указатель на метод.
- **Стабильный формат IO.** `UNIT_ATTACKED` остаётся одним событием на пару `(attacker, target)` за тик независимо от числа источников урона.
- **Тестируемость.** `IRandom` инжектируется, `World`/`Combat` не имеют глобального состояния.

## Недостатки и компромиссы
- **Бойлерплейт компонентов.** Каждое поведение — отдельный класс, даже если внутри одна строка. Для очень мелких механик это избыточно.
- **Снапшот = аллокация.** При каждом `emit`/`step` создаются временные `std::vector`. Для пошаговой симуляции это незаметно, но для real-time-цикла потребовалась бы пулизация (`small_vector`/арена).
- **Отсутствие настоящего ECS-storage.** Компоненты живут в `unique_ptr`, без archetype-таблиц и SoA-доступа. Это сознательный выбор простоты ради ясности; для тысяч сущностей пришлось бы менять хранение.
- **Семантика «обработчики не видят друг друга в текущем emit».** Удобна для предсказуемости, но иногда требует выноса логики в новый `emit` или в следующий тик. Этот контракт обязателен для разработчиков фич.
- **Атрибуция через `EntityId` после смерти источника.** Если охотник умер раньше последнего тика яда, событие урона всё равно атрибутируется ему. Это сознательное решение — иначе теряется учёт DoT.
- **Поиск компонента по интерфейсу — линейный** в пределах одного entity (обычно 5–10 компонентов). Для гипотетических entity с десятками компонентов один интерфейса можно перейти на упорядоченное хранилище, но в нашем масштабе это не нужно.
- **`callFirst` для не-`void` методов** возвращает `Ret{}` при отсутствии обработчиков — чистая семантика «значение по умолчанию», но требует, чтобы `Ret` был default-constructible. Альтернатива (`std::optional<Ret>`) усложнила бы вызывающий код; оставлено намеренно.

Проект использует CMake (минимум 3.27), стандарт C++20, генератор Ninja, сборка из IDE Visual Studio через CMake-интеграцию. Никаких внешних зависимостей.
