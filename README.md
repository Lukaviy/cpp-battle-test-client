## Правила симуляции
- Карта представляет собой прямоугольную сетку размером W×H клеток.
- Каждый юнит имеет уникальный целочисленный идентификатор.
- Один ход соответствует одному действию одного юнита.
- Юниты действуют в порядке их создания.
- Некоторые юниты могут перемещаться:
  - за один ход юнит может перейти в любую из 8 соседних клеток, если она свободна;
  - если цель недостижима за один ход, юнит продолжает движение к ней в последующих ходах.
- Некоторые юниты могут атаковать, уменьшая количество HP у цели:
  - при достижении 0 HP юнит умирает;
  - после смерти юнит больше не действует и освобождает занимаемую клетку.
- Симуляция завершается, когда не остаётся юнитов, способных совершать действия.

## Существующая реализация
При запуске приложение получает путь к файлу со сценарием симуляции.
Сценарий содержит команды для создания карты, юнитов и их перемещения.

Прототип содержит реализацию одного игрового юнита — мечника.

### Мечник
- **Ближняя атака**: атакует случайного юнита в соседней клетке, нанося урон, равный `Strength`.
- **Способность**: с вероятностью `Chance / 1000` вместо обычной атаки применяет «Рваные раны», нанося `Rending` урона.
- **Поведение**: если цель для атаки отсутствует, перемещается.

## Задача
Спроектировать и реализовать расширяемую архитектуру, затем продемонстрировать ее работу на примере нового юнита.

### Охотник
- **Дальняя атака**: стреляет в случайного юнита на расстоянии от 2 до `Range` клеток, нанося урон, равный `Agility`. Атака возможна только при отсутствии других юнитов в соседних клетках.
- **Ближняя атака**: если дальняя атака невозможна, атакует случайного юнита в соседней клетке, нанося урон, равный `Strength`.
- **Способность**: с вероятностью `Chance / 1000` вместо обычной дальней атаки применяет отравленные стрелы, нанося в сумме `Poison` урона за пять ходов.
  Урон от яда удваивается в тот ход, когда отравленный юнит получает эффект «Рваные раны».
- Урон от яда засчитывается как урон охотника, наложившего эффект.
- **Поведение**: если цель для атаки отсутствует, перемещается.

# Мысли при решении

Поток мыслей можно почитать в Thoughts.md, а здесь я кратко изложу основные идеи.

Самое базовое это добавлять новый функционал через композицию.
Делаем компоненты, которые реализуют определенные аспекты поведения юнитов, и комбинируем их для создания новых юнитов.

Подойти к реализации можно по разному, дефолт это `Entity Component`, где `Entity` это контейнер для компонент.
У `Entity` вызывается `update()`, тот пробегается по всем компонентам и вызывает их `update()`, а компоненты уже реализуют конкретное поведение.
Если им надо в `update()` они могут обращаться к другим компонентам, например, компоненту здоровья, чтобы нанести урон.
Подобную идею я реализовал в ветке `entity-component`.

Можно реализовать используя `Entity Component System` вместе с DoD, где у нас есть системы, которые обрабатывают данные юнитов. 
Например, система атаки будет обрабатывать всех юнитов с компонентом атаки, система перемещения будет обрабатывать всех юнитов с компонентом перемещения и так далее.
Но юниты ходят по одному друг за другом, так что выйгрыша по производительности не будет, возможно скорее наоборот.
Но реализовать что то подобное все равно было интересно.

## Архитектура

Идея состоит в следующем:
Есть системы которые подписываются на игровые события - просто глобальные функции.
События могут содержать данные, например какая сейчас фаза симуляции, сколько урона нанести и .т д.

Системы принимают это событие, некоторый контекст и список компонент которые должны быть у Entity.

Например, если нужно наносить урон от яда в конце хода, то система подписывается на событие TurnEndTick и принимает всех юнитов с компонентой `PoisonEffectComponent`.

```cpp
static void tick(
		const event::TurnEndTick& event,
		const core::EventContext& context,
		PoisonEffectComponent& poison_effect)
{
	const auto damageThisTick = std::min(poison_effect.damagePerTick, poison_effect.remainingDamage);
	behaviour::receiveDamage(context, poison_effect.sourceEntity, DamageUnit<DamageKind::Poison>{damageThisTick});
	poison_effect.remainingDamage -= damageThisTick;

	if (poison_effect.remainingDamage <= 0)
	{
		context.commands.removeComponent<PoisonEffectComponent>(context.entityId);
	}
}
```

Все ивенты настраиваются пользователями системы.
Например, для создания механики взаимодействия эффектов при получении урона, можно добавить событие `CollectReceiveDamageEvent`.

```cpp
struct CollectReceiveDamageEvent
{
	Damage damage;
};
```

Перед тем как нанести урон юниту, мы вызываем это событие, передавая ему информацию о том, какой урон должен быть нанесен.
Тогда подписчки с определенными компонентами смогут отреагировать на это событие и изменить урон.
Например, если Entity содержит эффекты "Рваные раны" и отравление, то урон от яда удваивается.

```cpp
registrator.handlers().add(
	+[](
	event::CollectReceiveDamageEvent& event,
	const core::EventContext&,
	RendingEffectComponent&,
	PoisonEffectComponent&)
	{
		event.damage.addMultiplier(DamageUnit<DamageKind::Poison>{1000});
	});
```

Здесь я использвал Multiplier у Damage, чтобы можно было накапливать процентный урон.
Но можно было бы и просто здесь урон от яда умножить на два.

Передаваемый объект события можно изменять внутри обработчика, и эти изменения будут видны всем последующим обработчикам, которые подписаны на это событие.

Поведения юнитов настраиваются аналогичным образом, через подписку на событие `ActionTick`.
Если на юните находится компонента `SwordsmanBehaviour`, то будет вызвана функция `tick`, которая реализует поведение мечника.

```cpp
void tick(
		const event::ActionTick&,
		const core::EventContext& context,
		const SwordsmanBehaviour& behaviour,
		component::PositionComponent& position,
		component::ActiveComponent& active,
		const component::UnitIdComponent& userId
		)
{
	active.active = false;

	if (const auto target_opt = findTargetForMeleeAttack(context, position.position))
	{
		const auto target = *target_opt;

		if (core::checkChance(context.random, behaviour.rendingAbilityChance))
		{
			context.commands.addComponent(target, component::RendingEffectComponent{});
			context.eventSystem.event(
					context.tick,
					io::UnitAbilityUsed{.abilityUnitId = userId.id.get_raw(), .abilityName = "rending"});

			attack(context, target, DamageUnit<DamageKind::Physical>{behaviour.rending});
		}
		else
		{
			attack(context, target, DamageUnit<DamageKind::Physical>{behaviour.strength});
		}

		active.active = true;
	}
	else if (moveUnit(context, position))
	{
		active.active = true;
	}
}
```

Движение юнита здесть реализовано в виде отдельной функции, которая может быть вызвана из разных обработчиков, если юниту нужно двигаться.
Кастомизация движения может быть сделана внутри этой функции путем проверки наличия определенных компонент у юнита.

```cpp
bool moveUnit(const core::EventContext& context, component::PositionComponent& position_component)
{
	if (auto* const move_target = context.components.getComponent<
		component::MarchTargetComponent>(context.entityId))
	{
		return basicMove(context, position_component, *move_target);
	}
	return false;
}
```

Либо как в случе с атакой на движение тоже можно сделать отдельный ивент и позволить обработчиком на него влиять.

В целом все механики поведения тут простые, перебор действий по порядку пока первое не отзовется.
Можно завести компоненту которая будет хранить список действий и систему которая будет их перебирать по порядку.
Архитектура позволяет сделать и так.

Но через отдельную функцию для каждого юнита мне показалось проще и гибче.

### Дефолтные ивенты
- `Add<T>{}` - добавление компоненты T. По умолчанию новая компонента затирает существующую.
- `AddExisting<T> { T& component; }` - добавление уже существующей компоненты T. Компоненту можно изменить прежде чем она перезапишет существующую.
- `Remove<T>{}` - удаление компоненты.
- `TickRoundStart{}` - событие при начале раунда. Начало цикла обхода всех юнитов.
- `TickTurnStart{ EntityId entityId; }` - Начало хода конкретного юнита. Вызывается для каждого юнита перед ходом каждого юнита.
- `TickAction{}` - событие для выполнения действия юнита.
- `TickTurnEnd{ EntityId entityId; }` - Конец хода конкретного юнита. Вызывается для каждого юнита после хода каждого юнита.

### Регистрация новых механик

Если на проекте работает 20 джунов одновременно и каждый копошится в районе механик взаимодействия,
то нужно минимизировать количество конфликтов при слиянии, а также сделать так, чтобы ребятки могли добавлять свои механики, не затрагивая чужой код.

Механики создаются в отдельных файлах, внутри объявляется функция `register"MechanicName"`, которая принимает класс `Registrator` и регистрирует все необходимые обработчики.

Пример регистрации юнита охотника:
```cpp

struct HunterBehaviour
{
	std::int32_t agility{};
	std::int32_t strength{};
	std::int32_t range{};
	std::int32_t chance{};
	std::int32_t poison{};
};

void registerHunter(core::Registrator& registrator)
{
	registrator.addSpawner(
			+[](const io::SpawnHunter& command, core::CommandBuffer& buffer)
			{
				buffer.spawnEntity(
						HunterBehaviour{
								.agility = static_cast<std::int32_t>(command.agility),
								.strength = static_cast<std::int32_t>(command.strength),
								.range = static_cast<std::int32_t>(command.range),
								.chance = static_cast<std::int32_t>(command.chance),
								.poison = static_cast<std::int32_t>(command.poison)
						},
						component::PositionComponent{.position = {.x = command.x, .y = command.y}},
						component::UnitIdComponent{
								.id = UnitId{command.unitId},
								.type = "hunter"
						},
						component::HealthComponent{.health = static_cast<int>(command.hp)},
						component::ActiveComponent{true}
						);
			}
			);

	registrator.handlers().add(&tick);
}
```

Затем вызов этой функции добавляется в функцию `registerAll`, где выполяется регистрация всех механик.
Тут хотя бы разрешение конфликтов при слиянии будет тривиальным.

Порядок вызова обработчиков событий определен порядком их регистрации, так что если нужно, чтобы механика отрабатывала раньше или позже другой механики, то это можно настроить просто изменив порядок регистрации.

Где нибудь здесь же можно было бы выполнять регистрацию комманд для парсера, чтобы все вообще в одном месте, но в Readme написано что менять можно только файлы внутри папки Game.

## Поведение механик

Поведение сделал как придумал. Поэтому яд наносит урон юниту в конце хода любого из юнитов, как я это понял из Readme.
Исходный код работал иначе.
Плюс не было написано, что должно происходить при отравлении юнита если тот уже отравлен.
Ради примера просуммировал урон от яда.

## Тесты

Тесты на всякий случай сделал чтобы проверить что поведение более менее соответствует требованиям.
Но их я просто навайбкодил.
Тесты сразу интеграционные, тестируется и парсер комманд и ивенты.

По умолчанию проект собирается без них, чтобы не выкачивать Catch2.
Чтобы их включить нужно передать флаг `-DBUILD_TESTS=ON` при сборке CMake.
Или воспользоваться готовой конфигурацией для Visual Studio, которая уже включает этот флаг.

## Минусы
Не стал заморачиваться с оптимизацией вызова обработчиков, они все вызываются последовательно для каждого юнита и у каждого запрашиваются нужные компоненты.
Можно сохранять список обработчиков для каждого юнита, сохранять маски компонент для обработчиков, и что нибудь еще можно придумать.

Не стал обновлять класс карты для поддержки юнитов с разным размером и разными масками коллизий.
Для добавления нового охотника в этом не было необходимости. А доделать в целом не составит труда.

Система не навязывает каких то конкретных паттернов при проектировании механик.
Придется писать гайды и говорить как как лучше делать и как лучше не делать.
Либо проектировать дополнительные системы взаимодействия которые архитектурно дают только одну возможную реализацию.

Как такового профита от плотной упаковки компонент нет. Разве что создание юнитов будет с минимумом аллокаций, если заменить std::unordered_map на что нибудь другое.
Можно отсортировать компоненты по порядку создания юнитов чтобы быстрее их обходить в цикле round().
В функции spawnEntity можно объявлять новую структуру которая будет содержать все компоненты юнита, функция шаблонная можно на месте сгенерить, и сохранять ее в виде одного объекта.
Все эти оптимизации не будут затрагивать пользовательский код.
